# CLAUDE.md - vault-service

## What this project is

A local ingestion service + web dashboard on top of a claude-obsidian vault (v1.9.2, Generic mode). It watches a folder and accepts drag-and-drop uploads, preprocesses material (PDF, Office, web, images, text), and runs headless Claude Agent SDK sessions that execute the vault's `ingest` skill fully automatically. A React dashboard exposes status, queue, chat with citations, and maintenance actions. Its shell is tabbed screens in the header row since the 2026-08 redesign, merged to main on 2026-08-27; SPEC.md §6 carries the correction table that describes them, and the pre-redesign subsections stay below it as the record of what was built against (see `docs/tasks/TASKS-REDESIGN.md`). **The screens are Home, Research, Graph, Catalog and System, plus Library when the agents are enabled.** The tabular view used to be called Library and was renamed Catalog on 2026-09-06, when the name went to the new room screen; that rename is the one visible change the base product took from the extension work.

**Two subsystems were added on top of this in 2026-09 and both have their own specification.** **Research agents ("Fellows")** are standing agents that plan from the vault's own open questions and work at night: `docs/agents/SPEC.md`, summarised in SPEC.md §12.10, and the whole subsystem is behind `AGENTS_ENABLED` (default off). **Source integrity** hardens how material is fetched and read - PDF URLs, the untrusted-content fence, open-access recovery, quote checking, the expand lock: `docs/sources/SPEC.md`, summarised in SPEC.md §12.11, and it is deliberately **not** behind a flag, because each part corrects the existing pipeline rather than adding a subsystem beside it.

**The authoritative specification is `SPEC.md` in this repo. Read it before any non-trivial task. When code and spec disagree, the spec wins; when you believe the spec is wrong, say so and ask before deviating.**

The vault itself lives OUTSIDE this repo (default `~/vault`, a claude-obsidian clone). Its path is a configuration value (`VAULT_ROOT`). Never hardcode it; pass it through explicitly (multi-vault support is a planned extension, see SPEC.md §12.1).

## Hard rules

1. **Vault integrity first.** The service writes to the vault only through agent runs, git commits, and **user-initiated page edits/deletes via `PUT`/`DELETE /api/v1/pages`** (added 2026-07-18, SPEC.md §12.4) and, since 2026-09-17, the user's strike-through of an open question via `POST /api/v1/questions/archive` (SPEC.md §12.4, `docs/agents/SPEC.md` 10.13), which edits exactly the bullet's own lines of the page it stands on - and every such mutation IS one immediate git commit behind the shared commit mutex, so it stays versioned and revertable and can never interleave with an agent commit. **The full writer list, which is the thing a change is checked against** (corrected 2026-09-19 after an audit found the rule naming four writers and the code holding nine; a new writer belongs in this list before it ships):

   | Writer | What it writes | Since |
   |---|---|---|
   | agent runs | wiki pages, `.raw/`, the hub pages | M0 |
   | `api/routes/pages.ts` | a user's page edit or delete (`PUT`/`DELETE /api/v1/pages`) | 2026-07-18 |
   | `pipeline/questions.ts` | the strike-through of one open question, exactly that bullet's own lines (`POST /api/v1/questions/archive`) | 2026-09-17 |
   | `pipeline/notebook.ts` | a Fellow's notebook page under `wiki/meta/agents/` | 2026-09-06 |
   | `pipeline/recap.ts` | the daily recap page under `wiki/meta/recaps/` | 2026-09-06 |
   | `pipeline/reading-list.ts` | the reading list page under `wiki/meta/` | 2026-09-06 |
   | `pipeline/link-repair.ts` | line-wrapped wikilinks joined back onto one line, on the pages carrying them | 2026-09-07 |
   | `api/routes/domains.ts` | the domain registry page (the vault's installed copy of `scripts/vault-extensions/domains.md`) | 2026-07-19, locked 2026-09-16 |
   | `pipeline/hubs.ts` | `wiki/index.md` (regenerated from page frontmatter) and the `wiki/log.md` entry, inside the run's own commit - see SPEC.md §12.12 | 2026-09-19 |

   Every one of them takes the vault's per-file lock first and commits behind the shared mutex; the hub writer is the one that does BOTH inside another run's commit rather than in one of its own, which is what keeps "one run, one commit" true; the grep that proves the list is complete is `grep -rn "withWikiLock" server/src`. Never delete or rewrite vault content from *pipeline* code. One sanctioned exception (added 2026-07-23, SPEC.md §12.6): pipeline code may run the vault's own deterministic retrieval-index scripts (`contextual-prefix.py`, `bm25-index.py`) as child processes - they write only derived, rebuildable artifacts under `.vault-meta/` (`chunks/`, `bm25/`, `embed-cache.json`), kept out of vault git history via `.git/info/exclude`; wiki content stays agent-run-only. A second sanctioned exception (added 2026-09-05, SPEC.md §12.9): when a job turns out to be a duplicate after preprocessing, pipeline code may remove its own never-committed `.raw/<job-id>/` staging dir, and only that, only when `git ls-files` knows nothing under it (`discardUntrackedDir`). A third sanctioned exception (added 2026-09-16, SPEC.md §12.4): every service writer of a wiki page first takes the VAULT's own per-file lock by running `scripts/wiki-lock.sh` as a child process - claude-obsidian makes that lock mandatory for every wiki page write from v1.7 on, our agent runs already obeyed it through its skills, and our own writers did not, which left a dashboard edit and an agent run on the same page covered by neither mechanism. It writes only `.vault-meta/locks/`, derived and self-reaping, the same category as the retrieval-index scripts. Take it OUTSIDE the commit mutex, never inside; a vault without the script is written unlocked rather than refused. SQLite holds operational state only; losing the DB must never damage the vault (SPEC.md §8).
2. **Localhost guard.** Server binds `127.0.0.1` by default. If bind ≠ localhost and no auth mode with a token/password is active, refuse to start (SPEC.md §9). Do not weaken this.
3. **Credentials** (`CLAUDE_CODE_OAUTH_TOKEN` or `ANTHROPIC_API_KEY`) live only in the service environment. Never in the repo, logs, frontend, or SQLite. Refuse to start if both are set (SPEC.md §7.1). Two sanctioned amendments (added 2026-07-19): with NO credential the service starts in **setup mode** (dashboard-only, nothing agent-running) instead of refusing, and `POST /api/v1/settings/credential` may write the credential into `~/.config/vault-service/env` (0600) - that file IS the service environment; the value must never be logged, returned, or stored elsewhere.
4. **Agent run permissions** (wording corrected from M0 evidence - read this before touching the runner's permission wiring):
   - **The hard, load-bearing guarantees:** writes confined to `VAULT_ROOT` (plus the sandbox's default temp allowlist), and no web egress in ingest runs. **Which runs DO reach the web has widened since this was written (2026-09-15):** the autoresearch flow, and every art of a Fellow's own research run - a watch, an explore and a deepening all read the web. What still never does is an INGEST run and a PLANNING run; the planner is deliberately confined to what the vault already holds (SPEC.md §12.10). Separately, the SERVICE makes outbound requests of its own during open-access recovery, which is service egress and not agent egress, the same distinction SPEC.md §9 draws for the Telegram bot (§12.11). These are enforced at the OS level by the Agent SDK's `sandbox` (bubblewrap on Linux): `sandbox: { enabled: true, failIfUnavailable: true, allowUnsandboxedCommands: false, filesystem: { allowWrite: [VAULT_ROOT] } }`. Deps: `bubblewrap` + `socat`.
   - **`canUseTool` is NOT the enforcement point - it was measured to be invoked zero times by this SDK.** Tool-level policy runs through a **`PreToolUse` hook**; the sandbox is what actually contains Bash. Do not "simplify" enforcement back to `canUseTool` or `permissionMode: 'acceptEdits'`. Do not set `allowUnsandboxedCommands: true` - the Bash tool ships a `dangerouslyDisableSandbox` escape hatch that is otherwise permitted by default, which makes the sandbox decorative.
   - **The bash denylist is defense in depth, not a hard boundary, and NOT a `scripts/*.sh` whitelist.** A scripts-only whitelist would block a real ingest (of 68 bash calls in the validated M0 run, 14 were `find`/`ls`/`cat`/`python3`). Deciding what an arbitrary shell string writes is not tractable; the sandbox, not the denylist, is what protects the vault.
   - **After any SDK upgrade or change to the permission wiring, re-run `server/src/cli/permprobe.ts`.** It is the only check that catches "the SDK stopped consulting our guard" - unit tests structurally cannot. Expect `canary outside vault: blocked`.
5. **Do not modify the cloned claude-obsidian repo internals.** Extensions to its behavior go through documented mechanisms only: the system-prompt extension in the agent runner, or a thin wrapper skill added to the vault (tracked in this repo under `scripts/vault-extensions/` and installed by a setup script). Both mechanisms are now in use: `RunAgentOptions.systemPromptExtra` carries the domain registry into every vault-writing run, and `scripts/vault-extensions/domains.md` is its seed page (installed by `scripts/install-domain-registry.sh`). Once installed, the VAULT's copy is the source of truth - the service only reads it.
6. Incoming files are never executed; magic-byte check against disguised executables; archives are not auto-extracted (v1). **And every converter that reads one runs contained** (added 2026-09-08, `server/src/pipeline/preprocess/sandbox.ts`): `pdftotext`, `pdfinfo`, `ocrmypdf`, `pandoc`, the Python office extractor, `exiftool` and `defuddle` all go through `runConverter`, which is bubblewrap with no network, no `$HOME`, a read-only `/usr` and `/etc`, the input file, and one writable output directory. This is hard rule 4's reasoning one stage earlier: a document reaches these parsers BEFORE any agent sees it, and `runTool`'s timeout is a liveness guard, not a boundary. Do not call `runTool` directly for a new converter, and do not widen `reads` to a home directory - bind the tool's own prefix (`toolPrefix`). `yt-dlp` is the one documented exception (it is a fetcher; the network is its job). A missing bubblewrap fails the conversion unless `PREPROCESS_SANDBOX=off`. **After any change to this wiring, re-run `server/src/cli/preprocprobe.ts`** - the same reason `permprobe` exists: unit tests read the policy, only the probe proves it is applied.
7. **This repo is PUBLIC; the vault is private.** Never let vault content leak into anything committed here - most easily missed in **commit messages and PR text**. Describe changes by their mechanism, not by the specific vault subject that motivated them: write "the single-post-creator class", never a real entity name, person, or `@handle` (this rule exists because a commit body once named two X handles from an entity page). A `commit-msg` hook (`scripts/git-hooks/commit-msg`, installed via `scripts/install-git-hooks.sh`, wired into `setup-all.sh`) blocks known entity/source names as a backstop - but it only knows names already in the vault, so it is not a substitute for writing generically. Overriding it with `ALLOW_VAULT_NAMES=1` needs a real reason.

   **What the hook cannot do, so nobody trusts it further than it goes (measured 2026-09-15).** It reads the commit MESSAGE, so a name in FILE CONTENT passes untouched - and content is where every leak of the 2026-09-15 audit actually was: examples in comments, UI placeholders, test fixtures, run output quoted into a design record. `gh pr create` text is not a commit message either, and the PR body is the likeliest leak of all. And it only knows page TITLES, so a subject that lives in the database (a Fellow's standing task) names things no title carries. Two of its three original blind spots were closed the same day - it reads title fragments now, and the buckets the research runs write - but the first limit is structural. **Before a PR: check the added lines and the PR text by hand**, and let `scripts/vault-name-scan.mjs` do the mechanical half of it: the same term-building as the hook, over file CONTENT rather than over a message, run as `--diff <base>` over what a merge would add and as `--file <path>` over the PR body before it is posted. It takes the wider list (concepts included), because a false positive there costs a glance and not a blocked commit. What stays a hand job is the third blind spot: a subject that lives only in the database carries no page title, so quoted run output is read with your own eyes.

8. **`AGENTS_ENABLED` is the extension gate, and the flag off must change nothing** (added 2026-09-15). The research agents (SPEC.md §12.10) exist only when it is set: no Fellow service, night shift, recap service, usage monitor or library service is constructed, their routes are not registered, `health.fellows` is false (a BOOLEAN - the startup banner's `on`/`off` is a different object, and `'off'` is truthy), and the dashboard neither renders a Fellow surface nor issues a request to a route only they own. That second half is the one that rots quietly: a query without an `enabled` guard costs one 404 per mount and nobody notices, which is exactly what two base-product screens were doing until 2026-09-15. Check it whenever a base-product screen gains a query. The reading list belongs to this subsystem too, prompt included: an ingest is told about it only behind the flag. **Source integrity (SPEC.md §12.11) is NOT behind this flag** and must not be put behind one - it corrects the existing pipeline, and a correctness fix behind a flag ships the known-weaker path as the default. `server/test/agents-flag-off.test.ts` holds the route half of this; the rest is read by hand.

## Conventions

- Node ≥ 20 LTS, TypeScript strict, ESM. Backend: Fastify, better-sqlite3, chokidar, zod. Frontend: React + Vite, TanStack Query, SSE (no WebSockets).
- All endpoints under `/api/v1/`, behind the auth middleware (v1 mode: `local-single-user`, pass-through). All new tables carry `user_id` (default `'local'`).
- **One ingest at a time.** The vault's ingest skill was built for single-writer use and says so (`skills/wiki-ingest/SKILL.md`, "Concurrency policy"); the service follows it, so the queue's default concurrency is **1** (corrected 2026-09-19, SPEC.md §3.1 - it was 2, and 13 of 31 finished jobs had overlapped another one). The setting still accepts more, and the settings UI says what would have to be true first.
- Job lifecycle states are exactly: `queued | preprocessing | ingesting | done | failed | deferred | duplicate | cancelled` (SPEC.md §8). Log every transition to `job_logs`.
- Preprocessing is a plugin chain (`detect → normalize → manifest`); new source types (e.g. future audio transcription) are added as plugins, never as special cases in the pipeline core. Every converter in the chain runs contained through `runConverter` (hard rule 6), and what a converter produces is fenced as data before any agent reads it (SPEC.md §12.11).
- Agent-run language rule: all wiki content in English regardless of source language; verbatim quotes keep their original language with a language note; check existing English concept names before creating new concept pages (SPEC.md §3.1).
- Tests: pipeline logic (queue transitions, dedupe, preprocessing, guards) gets unit tests; agent runs are mocked in tests. Fellow logic is tested the same way - the planner's prompt and its answer parsing, the gate, the shift's phases, the proposal lifecycle - with the runs themselves mocked. **`npm test`, `npm run typecheck` and `npm run lint` must all pass AND exit 0 before a milestone is called done.** Naming all three is not pedantry: `tsconfig.build.json` excludes `test/` and vitest does not typecheck, so a suite can be green while the typecheck is red, and both have been at once. A green suite is not a green repo.
- **After every vault upgrade, re-run `npm run vaultprobe`** (added 2026-09-19, `server/src/cli/vaultprobe.ts`). The service parses four texts the vault writes and owns none of them: the log entry crash recovery keys on, the lint report's headings, the paths the research prompt names, and the address rules the validator mirrors. Unit tests prove our parser still parses our fixture; only the probe proves the vault still writes what we read. The same reasoning as `permprobe` and `preprocprobe`, one layer out. `--ingest` adds a live run into a scratch vault; the default form reads files, writes nothing, and is safe against the live vault.
- Measurement before and after any vault-layer change: `node scripts/vault-audit.mjs <vault>` (read-only, `--json` for diffing two runs, `--redact` for the only output that may be committed here). The committed baseline is `docs/tasks/vault-audit-baseline-2026-09-19.json`.
- Commits: conventional style (`feat:`, `fix:`, `test:`, `docs:`), small and scoped. Do not commit generated artifacts.

## Working agreement

- Work milestone by milestone (M0-M5, SPEC.md §10). Each milestone's task list lives in `docs/tasks/`. Do not start Mn+1 while Mn acceptance criteria are unmet.
- At the start of a session, read the current milestone's task file and report which tasks are open before coding.
- When a task reveals a spec gap or a wrong assumption (e.g. the ingest skill behaves differently than expected), stop, document the finding in the task file, propose a resolution, and ask.
- Findings from the two M0 risk probes (Obsidian `\\wsl$` performance; ingest-skill interactivity) must be written down in `docs/tasks/TASKS-M0.md` - they decide follow-up work.

## Definition of Done (summary, details in SPEC.md §10)

- **M0:** one PDF ingested end-to-end via a CLI trigger; pages + index + hot cache correct; both risk probes documented.
- **M1:** 10 mixed files in `.raw` all reach `done`; no vault corruption at concurrency 2; retries/timeouts/dedupe work.
- **M2:** files dropped into the Windows watch folder land in the vault with zero interaction; batching within 60 s works.
- **M3:** browser drop → live log via SSE → resulting page links open in Obsidian.
- **M4:** chat answers cite clickable vault pages; lint report is structured; autoresearch and hot-cache refresh triggerable.
- **M5:** survives WSL restart via systemd user service; failed jobs diagnosable and retryable; settings UI; Dockerfile present; docs complete.
